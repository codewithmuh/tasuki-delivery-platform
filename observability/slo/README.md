# SLOs as code

Tasuki's service level objectives ([design §9](../../docs/design.md#9-slos)) are written as
[Sloth](https://sloth.dev) specs. Sloth turns each spec into Prometheus recording rules (the SLI at every window, the
remaining error budget) and multi-window, multi-burn-rate alerts. Generated rules are committed, so every change to an
SLO shows up in review as a diff of the real PromQL.

| Path | What it is |
|---|---|
| [specs/](specs/) | One Sloth `prometheus/v1` spec per service. **Edit these.** |
| [generated/](generated/) | Rules generated by `make slo-generate`. Never edit by hand; CI fails when they are stale. |
| [tests/](tests/) | `promtool test rules` unit tests: alerts fire when they should and stay quiet when they should not. |
| [../alerts/](../alerts/) | Hand-written cause and policy alerts (backlogs, drops, fallbacks, budget stages). |
| [docs/slo/error-budget-policy.md](../../docs/slo/error-budget-policy.md) | What happens when a budget runs low or runs out. |

```bash
make slo-generate   # specs → generated rules (needs sloth v0.16.0)
make slo-check      # promtool check rules + promtool test rules (needs promtool 3.x)
```

## The SLOs (P1)

All windows are 28 days rolling. Only production (namespace `tasuki-prod`) has SLOs; `tasuki-dev` shares the cluster
and Prometheus but not the objectives.

| Service | SLO (`sloth_slo`) | SLI: good events / all events | Target | Budget over 28 days |
|---|---|---|---|---|
| orders | `availability` | `POST /v1/quotes` and `POST /v1/orders` requests that are not 5xx | 99.9 % | 0.1 % of requests ≈ 40 min of full outage |
| orders | `latency` | `POST /v1/orders` requests faster than 300 ms | 95 % | 5 % of creates ≈ 33.6 h of everything slow |
| fleet-state | `location-freshness` | GPS points written to Redis within 2 s of `received_at` | 99 % | 1 % of points ≈ 6.7 h |
| tracking | `freshness` | Position events younger than 10 s when sent to a viewer | 99 % | 1 % of events ≈ 6.7 h |
| dispatch | `assignment-speed` | On-demand orders with an accepted courier within 60 s of confirmation | 95 % | 5 % of orders (≈ 2,500 a day at 50,000 orders/day) |

Ledger correctness, webhook timeliness and ETA accuracy (§9) belong to P3 services and are not defined yet.

### Metrics the SLIs need

| SLI | Metric | Status |
|---|---|---|
| orders availability | `http_requests_total{method, route, status}` (runtime contract); `route` is `/` + the Django route, e.g. `/v1/orders` | exported by `services/orders` |
| orders latency | `http_request_duration_seconds` histogram (runtime contract) with a **0.3 s bucket** (the client libraries' default buckets have none) | exported by `services/orders` |
| fleet-state freshness | `fleet_state_freshness_seconds` histogram: per live point written to Redis, `now − received_at`; 2 s bucket | exported by `services/fleet` |
| tracking freshness | `tracking_event_age_seconds{stream}` histogram: per position event sent to a viewer, `now − received_at`; 10 s bucket | exported by `services/fleet` |
| dispatch speed | `dispatch_assignment_duration_seconds{outcome="assigned"\|"no_courier"}` histogram: once per order at `CourierAssigned` or the first `NoCourierAvailable`, timed from `OrderConfirmed.occurred_at`; 60 s bucket. Good = `assigned` within 60 s, so a no-courier order is always bad | agreed with the dispatch agent; dispatch is being built |

`namespace` and `service` come from the Prometheus scrape (ServiceMonitors keep the default `service` label).

Prometheus 3 stores classic-histogram bucket bounds as floats, so the specs select `le="2.0"`, `le="10.0"` and
`le="60.0"` (and `le="0.3"`) whatever the client library prints.

## Burn-rate alerts

Sloth uses the [SRE Workbook](https://sre.google/workbook/alerting-on-slos/) parameters, which define each alert by the
share of the period's budget it allows to burn:

| Alert | Long / short window | Budget burned in the long window | Burn rate on 28 days | Budget gone in | orders availability fires at |
|---|---|---|---|---|---|
| page | 1 h / 5 m | 2 % | 13.44× | ~2 days | 1.34 % errors |
| page | 6 h / 30 m | 5 % | 5.6× | 5 days | 0.56 % errors |
| ticket | 1 d / 2 h | 10 % | 2.8× | 10 days | 0.28 % errors |
| ticket | 3 d / 6 h | 10 % | 0.93× | 30 days | 0.093 % errors |

The familiar 14.4× / 6× / 1× are the same rule on a **30-day** period. On our 28-day period the same budget shares give
13.44× / 5.6× / 0.93×. We keep Sloth's built-in `google-28d` windows (`--default-slo-period=28d`) instead of
forcing 14.4× through a custom windows file, whose percentages would need float tricks and still render as
`5.999999999999999` in the rules. Sloth's ticket alert also includes the 1 d / 2 h pair.

Both windows of a pair must be over the threshold. The long window proves the burn is real; the short window makes
the alert stop within minutes of the fix. Sloth alerts have no `for:`; the windows do that job. Page and ticket share
one alert name per SLO and differ by the `severity` label (`page` or `ticket`). Every alert carries a `runbook_url`.

## No traffic, no NaN

Two guards are in every SLI query, and the unit tests check both:

- **`or vector(0)` on the error side.** A counter like `status="503"` does not exist until the first 503. Without the
  guard, a healthy service has *no* error ratio rather than a ratio of 0.
- **`> 0` on the total side.** With no requests in a window, `errors / total` is `0/0 = NaN`. Sloth's 28-day ratio
  averages the 5-minute ratios, so one NaN would poison the whole budget for 28 days, and the rollout gate would read
  "no data" and block every deploy. With the guard, an idle window records nothing and is left out of the average.

Each guard covers a different "no events" case: one is "no errors yet", the other is "no traffic at all". Neither
covers a component that has stopped emitting events, so each SLI is paired with a backlog alert in
[../alerts/](../alerts/): outbox lag for dispatch, consumer lag for fleet-state and tracking, dropped events for
tracking.

Two Sloth details worth knowing:

- `slo:period_error_budget_remaining:ratio` is `1 − (28-day error ratio ÷ budget)`: 1 is untouched, 0 is spent, and it
  goes negative when the budget is overspent. It carries `sloth_window="4w"`. The rollout gate reads it.
- The 28-day ratio is the **average of 5-minute ratios** (time-weighted), not total errors ÷ total requests over 28 days
  (event-weighted). A bad quiet hour counts as much as a bad busy hour, which is stricter at night.

## In the cluster

These files are plain Prometheus rule groups (`groups:`), which is what `promtool` checks and tests. The GitOps layer
wraps them in `PrometheusRule` objects for kube-prometheus-stack.

Sloth also has a Kubernetes form of the same spec, the `PrometheusServiceLevel` CRD. There are two ways to use it:

1. **Sloth controller.** Install the Sloth Helm chart. It watches `PrometheusServiceLevel` objects and writes the
   `PrometheusRule` for each one.
2. **Offline.** Run `sloth generate -i orders.yaml` on a CRD file. It prints a ready `PrometheusRule`, with no
   controller in the cluster.

```yaml
apiVersion: sloth.slok.dev/v1
kind: PrometheusServiceLevel
metadata:
  name: orders
  namespace: monitoring
spec:
  service: orders
  slos:
    - name: availability
      objective: 99.9
      sli:
        events:
          errorQuery: sum(rate(http_requests_total{namespace="tasuki-prod",service="orders",method="POST",route=~"/v1/quotes|/v1/orders",status=~"5.."}[{{.window}}])) or vector(0)
          totalQuery: sum(rate(http_requests_total{namespace="tasuki-prod",service="orders",method="POST",route=~"/v1/quotes|/v1/orders"}[{{.window}}])) > 0
      alerting:
        name: OrdersAvailabilityBudgetBurn
        labels: { category: availability }
        annotations:
          runbook_url: https://github.com/codewithmuh/tasuki-delivery-platform/blob/main/docs/runbooks/slo-orders-availability.md
        pageAlert: { labels: { severity: page } }
        ticketAlert: { labels: { severity: ticket } }
```

We use the plain `prometheus/v1` specs with committed output for three reasons. Reviewers see the generated PromQL
change. The unit tests run against exactly the rules that ship. And the cluster needs no extra controller.

## Adding or changing an SLO

1. Edit or add `specs/<service>.yaml`. Keep `alerting.annotations.runbook_url` pointing at a runbook in
   [docs/runbooks/](../../docs/runbooks/), and write that runbook in the same pull request.
2. Run `make slo-generate`, then `make slo-check`. Add a test in `tests/` for any new SLI shape.
3. Commit the spec, the generated file and the tests together.
