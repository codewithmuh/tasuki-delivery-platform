Why it exists

Taking orders was the easy part.

When customers start asking for delivery, you need a second system. It must track every moving driver every few seconds, assign the right one in under a minute, never lose or double-book an order, and keep each customer's map live. That is a different kind of software from a shop or an ordering app, and it should not share a server with one. Tasuki is that system, ready to deploy next to yours.

Live location at scale

GPS updates flow through Kafka, not your main database. Hundreds a second never slow your shop down.

Orders never lost or doubled

Idempotency keys, a transactional outbox and deduplicated events make every retry safe.

Customers see their delivery

A signed tracking link per order, live in any phone browser. Nothing to install. English and Japanese.

Runs in your account

Your cloud, your region, your data. No per-delivery fee to a vendor and no lock-in. MIT licensed.

How it works

Every order is handed on, never dropped.

A 襷 (tasuki) is the sash that ekiden relay runners hand to each other. Tasuki hands every order on the same way: your system, then dispatch, then a driver, then your customer. The platform's job is to make sure the sash is never dropped, never handed to two runners, and always visible.

  1. 1

    Your system creates the delivery

    Ask for a price and an ETA, then create the order with an Idempotency-Key. You get an order ID and a tracking link for your customer.

    POST /v1/quotes · POST /v1/orders
  2. 2

    Dispatch finds a driver

    The nearest free driver gets an offer with a 30-second timer. On a decline or a timeout, the next one does. Travel times come from real roads (OSRM).

    offers over server-sent events
  3. 3

    Drivers move, customers watch

    The driver's phone sends GPS in small batches. Your customer's tracking page moves the marker live and keeps the ETA honest.

    POST /v1/locations · GET /v1/track/…/stream
  4. 4

    Your system stays in sync

    Every change (confirmed, assigned, picked up, delivered) is an event with a full history. Signed webhooks that push it to you are next on the roadmap.

    GET /v1/orders/{id} · webhooks (next)

Integrate

A few HTTP calls, not a migration.

Keep your shop, your app and your database. Tasuki sits beside them and talks plain JSON over HTTPS. These are the real endpoints: run make up and they answer on your laptop. 

# Locally (make up): ORDERS=http://localhost:8000

# 1. Ask for a price and an ETA. A quote is valid for 2 minutes.
curl "$ORDERS/v1/quotes" \
  -H "Authorization: Bearer $TASUKI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "store_id": "str_01JA2Q…",
    "dropoff": {
      "lat": 35.6618, "lng": 139.6983, "ward": "shibuya",
      "address": "1-2-3 Jinnan, Shibuya-ku",
      "customer_name": "Sato Hana", "customer_phone": "090-1234-5678"
    }
  }'
# 201 {"quote_id": "quo_01JA2R…", "fee_yen": 742, "eta_seconds": 1920, "expires_at": "…"}

# 2. Turn the quote into an order. Retrying with the same key never creates a second one.
curl "$ORDERS/v1/orders" \
  -H "Authorization: Bearer $TASUKI_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: checkout-8812" \
  -d '{"quote_id": "quo_01JA2R…"}'
# 201 {"order_id": "ord_01JA2S…", "status": "confirmed", "tracking_url": "…/track/eyJhbGci…"}
// Send your customer the tracking_url as it is (a hosted page in English and Japanese),
// or draw the delivery inside your own app. Locally: TRACKING = "http://localhost:8083".
const stream = new EventSource(`${TRACKING}/v1/track/${token}/stream`);

stream.addEventListener("status", (e) => {
  const { status, eta } = JSON.parse(e.data); // confirmed → assigned → picked_up → delivered
  renderStatus(status, eta);
});

stream.addEventListener("position", (e) => {
  const { lat, lng } = JSON.parse(e.data); // the assigned driver, every few seconds
  moveDriverMarker(lat, lng);
});

// delivered, cancelled, failed or expired: the server closes the stream
stream.addEventListener("end", () => stream.close());
# What a driver app sends. Locally: FLEET=http://localhost:8081, DISPATCH=http://localhost:8082

# Every few seconds while moving: a batch of 1 to 50 GPS points.
curl "$FLEET/v1/locations" \
  -H "Authorization: Bearer $DRIVER_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"points": [{
        "lat": 35.6581, "lng": 139.7017, "accuracy_m": 8,
        "speed_mps": 4.2, "heading_deg": 90,
        "device_time": "2026-10-16T03:12:08Z",
        "status": "to_dropoff", "order_id": "ord_01JA2S…"
      }]}'
# 202 {"accepted": 1, "dropped": 0}  (503 + Retry-After when the platform sheds load)

# Offers arrive on a stream. The driver has 30 seconds to answer.
curl -N "$DISPATCH/v1/couriers/me/offers/stream" -H "Authorization: Bearer $DRIVER_TOKEN"
curl -X POST "$DISPATCH/v1/offers/off_01JA2T…/accept" -H "Authorization: Bearer $DRIVER_TOKEN"

# Proof of delivery: the driver must be within 500 m of the drop-off.
curl -X POST "$ORDERS/v1/courier/orders/ord_01JA2S…/deliver" \
  -H "Authorization: Bearer $DRIVER_TOKEN" -H "Content-Type: application/json" \
  -d '{"lat": 35.6619, "lng": 139.6981}'
# Today: read an order with its full status history.
curl "$ORDERS/v1/orders/ord_01JA2S…" -H "Authorization: Bearer $TASUKI_API_KEY"

# Next on the roadmap: signed webhooks to your endpoint, retried until it answers 2xx,
# signed with HMAC-SHA256 over a timestamp and the body, with a 5-minute replay window.
# They carry the events the platform already publishes inside, for example:
{
  "schema": "order.event.v1",
  "event_id": "evt_01JA2V…",
  "type": "OrderPickedUp",
  "order_id": "ord_01JA2S…",
  "merchant_id": "mer_01JA2P…",
  "occurred_at": "2026-10-16T03:14:41Z"
}

Architecture

Two systems with different rules.

Orders are few and precious. Locations are many and disposable. Tasuki keeps the two apart, so a flood of GPS points can never stop an order, and the order path never trades correctness for speed.

Orders and moneyLocations and tracking
Volume at peakSingle-digit writes a second, even in a surgeAbout 750 GPS updates a second
"Correct" meansExactly-once effects: never lost, never charged twiceLatest wins: a missed point is harmless if the next one arrives
Source of truthPostgreSQL, with a transactional outboxThe Kafka log; Valkey is a cache rebuilt from it
On failureReject or queue, never guessServe the last known position and say how old it is
LanguagePython and Django: rich domain model, transactionsGo: high throughput, small memory, cheap concurrency
Why server-sent events and not WebSockets?

Tracking only flows one way, from the platform to the screen. Server-sent events run over plain HTTP, pass through proxies and load balancers without special setup, and reconnect on their own. Drivers send GPS the other way as small batched HTTPS requests, which survive flaky mobile networks better than a long-lived socket.

Scale

Sized for 1.5 million orders a month in one city.

Every design choice has a number behind it. These are the targets for a busy city operator, with room for a rainy Friday, when demand triples and every customer is watching the map.

50,000orders a day, 12 % of them in the busiest hour
20/sorder capacity: a 3× rain surge with 4× headroom
750/sGPS updates from 3,000 drivers at peak
10,000customers watching live at the same time

These are design targets, not measurements yet. The simulator already has a design-scale rainy-Friday scenario. Load-test results will be published here with the scripts to reproduce them, and not before.

A surge is a capacity problem, not a throughput problem

At three times normal demand, orders want 18,000 deliveries an hour while drivers can do about 7,200. The servers cope easily; what breaks is the promise. So in a surge Tasuki quotes honestly: longer ETAs, fewer bookable windows, a surge fee. And it stays up.

Built to scale out

Every service is stateless and scales horizontally behind Kubernetes. Kafka is keyed by driver and by order, so each one's events stay in order while consumers spread across partitions. Karpenter adds spot nodes when load rises and removes them after.

When things break

Designed to bend, not fall over.

Every part fails eventually. Each failure below has a planned response, and each one becomes a game-day experiment with a written postmortem.

FailureWhat your customers seeWhat Tasuki does
Valkey (cache) lostNothing on orders or tracking; new assignments pause for secondsTracking reads Kafka, not the cache. fleet-state replays recent locations to rebuild it; dispatch waits for the rebuild.
Kafka unavailableOrders still accepted; status updates lateOutbox rows wait in PostgreSQL and drain later. Ingest sheds load with Retry-After.
Database failoverOrder creation fails for 1 to 2 minutesClients get 503 with Retry-After. Idempotency keys make every retry safe.
Routing (OSRM) downETAs a little less exactDispatch falls back to straight-line distance with a detour factor, and widens quotes.
Rain surge (3× demand)Longer ETAs, fewer windows, a surge feeQuotes follow driver supply. Priority shedding: orders, then dispatch, then tracking, then history.
One availability zone lostBrief retriesPods spread over three zones with disruption budgets; Multi-AZ database; Kafka replication factor 3.

  • Observability as code. OpenTelemetry in every service; Prometheus, Loki, Tempo and Grafana dashboards kept in git.

Built in Tokyo

Ready for Japan. 日本の配送にも対応

The reference deployment covers Tokyo's 23 wards on real Tokyo roads. Japanese delivery has its own rules, so they are built in from the start.

  • Data stays in Japan. Everything runs in AWS Tokyo; disaster-recovery copies are designed to go only to Osaka.
  • APPI-minded. Customer names, phones and addresses are encrypted per field and never appear in events or logs.
  • Yen done right. Integer yen, 10 % consumption tax rounded down once per order (端数切り捨て).
  • Bilingual. The tracking page speaks English and Japanese.
  • Delivery windows. 時間帯指定 booking without overbooking is on the roadmap.

Questions

Before you ask.

Is it free?

Yes. Tasuki is MIT licensed: run it, change it and use it commercially. You pay only for the cloud resources you run it on.

Can I use it outside Tokyo today?

Not yet. The service area, the zones and the pricing are Tokyo's for now. Making them configurable for any city is the first item on the "Next" list.

Do I need Kubernetes?

Not to try it: Docker Compose runs the whole stack on one machine. The production path today is Kubernetes. A single-server production install for smaller teams is on the roadmap.

Where does my data live?

In your own cloud account and the region you choose. Tasuki sends nothing anywhere else.

Is there a driver app?

Not yet. The simulator plays every driver through the same public API a real app will use, so any app can integrate today. A driver app is on the "Next" list.

Is this a real company?

Tasuki is an open-source project, not a delivery company. The merchants, drivers and customers in the demo are generated by the simulator. The software, the infrastructure and the reliability work are real.
